# 💬 CBODY 客户端即时通讯与推送系统

## 🎯 设计目标
- **极致节流**：非聊天状态不维持 Realtime 连接  
- **即时体验**：聊天会话页 0 延迟实时更新  
- **精准推送**：仅后台/非活跃时触发推送（同线程 30s 去重）  
- **UI 一致性**：角标与聊天列表统一同步逻辑  

---

## 🧱 一、全局运行逻辑

| 模块 | 是否启用 Realtime | 更新机制 |
|------|------------------|-----------|
| 首页 / 技师详情 / 用户中心 | ❌ | 缓存 + 定时拉取(已实现 不修改) |
| 聊天列表页 | ❌ | 30s 轮询 RPC |
| 聊天会话页 | ✅ | 实时订阅当前线程 |
| 底部角标 | 条件启用 | 依附列表数据或独立轮询 |
| 后台状态 | ❌ | 关闭 Realtime，依赖推送 |

### 除了会话页 聊天列表页 底部角标，其他页面 我们统称为**其他页面**
---

## 🧩 二、推送静默机制（前台静默，后台显示）
- **不使用心跳机制**，改用 AppState 判断前台/后台状态  
- 推送通知始终发送，但显示由客户端控制：
  - 前台 (`AppState.currentState === 'active'`) → 🔇 静默接收（不显示）  
  - 后台/关闭 → 📣 显示推送通知  
- 优势：
  - ✅ 零数据库写入压力（无心跳UPDATE）
  - ✅ 逻辑简单可靠（客户端自主判断）
  - ✅ 服务器推送逻辑简化（无需判断 last_seen_at）

---

## 🟢 三、聊天会话页（唯一实时模块）

**核心目标：必须实时、前台不推送**

```

进入会话页
↓
建立唯一 Realtime socket
↓
订阅频道 thread:{id}
↓
收到消息 → 即时渲染（不推送）
↓
离开页面 → unsubscribe 当前频道
若无其它频道 → 关闭 socket

```

- 每次只订阅一个线程频道（切换会话时先取消再订阅）。  
- 同一 socket 循环复用，不重新创建。  
- 离开后立即清空未读并同步角标状态。  

---

## 🟡 四、聊天列表页（会话汇总）
**目标：轻量实时感，无 socket 占用**

- 不订阅任何频道。  
- 每 30 秒轮询 RPC 获取：
  - 会话摘要  
  - 各线程未读数  
  - 全局未读汇总  
- 拉取结果写入全局状态（如 `useUnreadStore`）。  
- 离开页面停止轮询。  
- 进入聊天会话页时：列表轮询暂停，由会话页接管实时。  


> ✅ 聊天列表 = 未读源头  
> ✅ 底部角标实时同步列表结果  

---

## 🔴 五、底部角标逻辑（未读汇总）

**目标：省流但始终反映真实状态**

### 前台逻辑：
| 场景 | 数据来源 |
|------|------------|
| 用户在聊天列表页 | 直接使用列表全局状态（即时同步） |
| 用户不在聊天页 | 每 60 秒轮询一次 RPC 轻量拉取 |

### 后台逻辑：
| 场景 | 行为 |
|------|-------|
| App 进入后台 | 停止轮询，不更新角标 |
| 技师发来消息 | 服务器触发推送（始终发送） |
| 用户回到前台 | 再次拉取一次角标汇总，立即刷新 UI |

> 💡 角标只在前台存在"感知"；后台完全交给推送处理。  

---

## 🔔 六、推送策略

- **触发条件**
  - 新消息产生时始终推送  
  - 同线程 30 秒内去重（防止重复推送）  

- **前台活跃时**
  - 推送仍然发送，但客户端静默接收（不显示通知）
  - Realtime 负责实时更新UI

- **后台或关闭时**
  - 推送显示通知
  - 消息抵达后更新角标数（用户回前台时刷新）

---

## ⚙️ 七、App 前后台切换逻辑

| 状态切换 | 动作 |
|-----------|------|
| → 前台 (`active`) | 恢复角标/聊天列表轮询；推送静默接收 |
| → 后台 (`background`) | 停止轮询；断开 Realtime；推送正常显示 |
| → 回前台 | 拉取角标汇总 + 聊天摘要；根据页面决定是否恢复 Realtime |

---

## 🧠 八、连接与节流控制

| 项目 | 策略 |
|------|-------|
| Socket | 全局仅 1 条；由会话页复用 |
| 推送显示控制 | AppState 判断（前台静默，后台显示） |
| 聊天列表 | 30 秒轮询 |
| 角标独立轮询 | 60 秒（仅非聊天页） |
| 推送防抖 | 同线程 30 秒内仅一次 |
| 数据缓存 | React Query + staleTime 5~10 分钟 |

---

## ✅ 九、用户体验对照表

| 场景 | 行为 | 体验 |
|------|------|------|
| 非聊天页面 | 无 Realtime；可接受轻微延迟 | 稳定、省电 |
| 聊天列表页 | 轮询更新；角标同步 | 延迟 ≤30s |
| 聊天会话页 | 实时消息，无推送 | 零延迟 |
| 切后台 | 断开 Realtime；由推送接管 | 安静节流 |
| 回前台 | 即时同步角标 + 列表 | 无感恢复 |

---

## 🧩 十、系统结果

| 目标 | 达成情况 |
|------|------------|
| 即时性 | 聊天页全实时 |
| 节流 | 绝大部分时间无 Realtime |
| 推送准确性 | 仅离线触发、30s 去重 |
| 角标同步 | 全局单一来源（聊天列表） |
| 成本 | 极低连接数、最少写入频率 |

---

## 🏁 结论
> App 仅在"沟通态"保持 Realtime；  
> 所有"浏览态"一律靠缓存 + 轮询；  
> 前台推送静默 + 轮询维持轻量同步；  
> 后台由推送接管，30 秒防抖。  

**最终效果：**
- 用户体验无感延迟；  
- 系统连接数稳定；  
- **零数据库心跳写入压力**（相比心跳方案节省 100% UPDATE）；
- 成本与耗电最低。
